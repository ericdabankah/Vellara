# VELLARA Property Assets & Media Management

**Status:** implementation contract draft  
**Branch:** `feat/property-assets-media-contract`  
**Depends on:** property foundation and Owner Desk property-readiness work  
**Production impact:** none. This document defines the next implementation increment. It does not create a bucket, table, policy, API route, or production data.

## 1. Purpose and scope

Give each VELLARA property an owner-managed media library. The same property-level asset model supports both current verticals:

- **Hospitality:** property exterior, interiors, amenities, views, and other property-gallery images.
- **Real estate:** property exterior/interior photographs, views, and floor-plan images.

The first increment is property-level images only. It does not create room-level media, a real-estate listing/offer model, video hosting, document storage, image editing, or a mini-site page builder. Those are separate increments.

A property's media library is not automatically public. Uploading an image and publishing an image are distinct actions.

## 2. Architecture decision

Use a **private Supabase Storage bucket** and let the VELLARA backend control upload authorization, publication, and customer delivery.

- Supabase Storage stores the binary image.
- A `public.property_assets` row stores tenant/property ownership and media metadata.
- The VELLARA backend validates the caller's membership and active property assignment before issuing a signed upload URL.
- The browser uploads directly to Storage using that short-lived signed URL. It never receives a service-role or secret key.
- The backend finalizes the upload only after verifying that the object exists and its actual size and content type match the allowed limits.
- The public mini-site asks the backend for published media. The backend returns short-lived signed read URLs only for ready, published assets on an active property.

This keeps private drafts private and avoids turning the entire bucket public merely because one image is published.

## 3. Data model proposal

Add `public.property_assets` in a forward-only migration after the property foundation is integrated.

| Column | Type | Purpose |
|---|---|---|
| `id` | uuid | Asset identity, generated by Postgres |
| `organization_id` | uuid | Tenant scope |
| `property_id` | uuid | Parent property |
| `storage_path` | text | Exact private-bucket object path, unique |
| `original_filename` | text | Sanitized display-only filename |
| `mime_type` | text | Verified image MIME type |
| `byte_size` | bigint | Verified object size |
| `width`, `height` | integer, nullable | Server-derived image dimensions |
| `category` | text | `exterior`, `interior`, `amenity`, `view`, `floor_plan`, `other` |
| `alt_text` | text | Accessibility text; required before publication |
| `caption` | text | Optional customer-facing caption |
| `display_order` | integer | Stable gallery ordering |
| `is_cover` | boolean | Property cover-image selection |
| `is_published` | boolean | Customer-facing visibility |
| `upload_status` | text | `pending`, `ready`, `failed` |
| `uploaded_by` | uuid | Authenticated uploader |
| `created_at`, `updated_at` | timestamptz | Audit timestamps |
| `archived_at` | timestamptz, nullable | Soft archive; no browser hard-delete |

### Required constraints and indexes

- Composite foreign key `(organization_id, property_id)` to `properties(organization_id, id)`.
- Unique `storage_path`.
- `byte_size > 0` and bounded by the configured upload limit.
- Positive dimensions when present; bounded filename, caption, and alt-text lengths.
- Allow-listed image MIME types only: JPEG, PNG, WebP, and AVIF for this first increment.
- `display_order >= 0`.
- Published assets must be `ready`, not archived, and have non-empty alt text.
- At most one active, ready, published cover asset per property using a partial unique index.
- Index by `(organization_id, property_id, archived_at, display_order)` for Owner Desk gallery reads.
- Index the public lookup path by property and publication state.

The browser must not be trusted to supply `organization_id`, `uploaded_by`, `byte_size`, `mime_type`, or image dimensions as authoritative values. The backend derives tenant and actor identity from the authenticated request and verifies object metadata before finalization.

## 4. Storage layout and upload limits

Create one private file bucket named `property-media`.

Canonical object path:

```text
<organization_uuid>/<property_uuid>/<asset_uuid>/<randomized_filename>
```

The original filename is display metadata only. It must not be used as a trusted path segment. The asset UUID and randomized filename prevent accidental overwrite and make each upload immutable.

Initial upload rules:

- Images only, no SVG.
- JPEG, PNG, WebP, AVIF.
- Maximum 20 MiB per image.
- No client-side `upsert`; use a new object path for every replacement.
- The backend verifies actual object size and MIME type before changing `upload_status` to `ready`.
- Image transformations/derivatives are a later optimization, not a prerequisite for correctness.

The exact bucket settings and object policies must be created in the migration/release workflow, not by an Owner Desk browser session.

## 5. Authorization contract

Use the existing two-part authorization model:

1. Organization membership determines the user's role.
2. An active property assignment scopes non-owner access to a property.

Initial media permissions:

| Capability | Owner | Assigned manager | Assigned operations | Assigned verification |
|---|---:|---:|---:|---:|
| View property media in Owner Desk | Yes | Yes | No initially | No |
| Upload images | Yes | Yes | No | No |
| Edit caption, alt text, category, order | Yes | Yes | No | No |
| Select/replace cover image | Yes | Yes | No | No |
| Publish/unpublish | Yes | Yes | No | No |
| Archive an asset | Yes | Yes | No | No |
| Read published media as a public customer | Public endpoint only | Public endpoint only | Public endpoint only | Public endpoint only |

Owners retain organization-wide property access according to the existing `private.has_property_role` helper. Managers require an active assignment to the target property. Do not infer access from a client-supplied organization or property ID.

### Database and Storage policies

- Enable RLS on `public.property_assets`.
- Authenticated table access is limited to the owner/manager property scope.
- Keep writes to an allow-list of mutable metadata columns. Identity, tenant scope, property scope, uploader, storage path, verified size/type, and upload state are server-controlled.
- Storage has its own RLS policies on `storage.objects`; application-table RLS does not protect files automatically.
- The private bucket must not grant anonymous reads.
- Signed upload/read URLs are short-lived capabilities. The backend must authorize before issuing them.
- Never expose a service-role or secret key to the browser.

The Storage policies must bind an object path to a pre-created `property_assets` row and the same organization/property scope. Do not authorize uploads merely because a path begins with a user-supplied organization UUID.

## 6. Upload and publication lifecycle

1. Owner/assigned manager selects a property and chooses images.
2. Frontend asks the VELLARA backend to create an asset upload intent with category, display filename, caption, and alt text.
3. Backend authenticates the caller, resolves the tenant from membership, verifies active property assignment and property status, creates a `pending` metadata row, and returns a short-lived signed upload URL/token bound to the exact object path.
4. Browser uploads the image directly to the private bucket. It does not use `upsert`.
5. Frontend calls the backend to finalize the upload.
6. Backend verifies object existence, actual MIME type, actual size, and image dimensions. It marks the row `ready` only after those checks pass. Failed uploads remain retryable or are expired by cleanup.
7. Owner/manager edits metadata and reorders images.
8. Publishing requires a ready, non-archived image, valid alt text, and an active property.
9. The mini-site backend returns only published, ready assets belonging to the requested active property. It creates short-lived signed read URLs at request time.
10. Replacing an image creates a new asset/object. The old image remains until the replacement is ready and the owner confirms the change. Archive is soft; physical cleanup is a trusted server task.

Do not persist signed URLs in the database. Persist only the bucket and object path. Signed URLs expire and must be refreshed by the backend.

## 7. Backend contract for the backend developer

The backend module must expose equivalent operations, using the repository's agreed API prefix and response envelope:

- Create upload intent for a property.
- Finalize/verify an uploaded object.
- List property assets for an authorized Owner Desk user.
- Update allow-listed metadata and ordering.
- Publish/unpublish an asset.
- Soft-archive an asset.
- Resolve published media for a public property mini-site.

Every operation must resolve tenant identity from the authenticated session and re-check property authorization. Public media resolution must use the public property slug, require an active property, and return only published, ready, non-archived assets. It must not accept arbitrary bucket names or object paths from the caller.

The repository's API prefix/envelope mismatch is still an open integration contract. This document intentionally defines operations and security behavior, not a competing route convention.

## 8. Audit and failure handling

Record trusted audit events for upload intent creation, upload finalization, metadata changes, publish/unpublish, cover selection, and archive. Actor and tenant identifiers are derived server-side. Do not put signed URLs, secrets, or raw image bytes in audit metadata.

Handle partial failures explicitly:

- Intent created, upload not completed: expire and clean up the pending row/object.
- Object uploaded, finalization failed: retain pending state for safe retry; never publish.
- Metadata update failed: leave the last valid metadata untouched.
- New cover selected: transactionally unset the previous cover and set the new ready/published asset.
- Archive requested: remove from Owner Desk/public resolution immediately, then delete the binary through the Storage API in a trusted cleanup process after the retention window.

Do not delete rows directly from `storage.objects`. Use the Storage API for object lifecycle operations.

## 9. Required tests before release

### Tenant and property isolation
- Owner can manage media for all properties in their organization.
- Manager can manage media only for assigned properties.
- Manager cannot upload, list, publish, or archive media for another property.
- Operations and verification roles cannot use Owner Desk media-management operations.
- Cross-organization property IDs and guessed object paths are denied.
- Revoked assignment immediately removes media-management access.

### Upload security
- Unsupported MIME type, oversized file, malformed path, and mismatched object metadata are rejected.
- A caller cannot finalize another user's pending asset.
- A caller cannot change tenant/property IDs, storage path, uploader, verified size/type, or upload status.
- Re-uploading an existing object path is rejected; replacements use new paths.
- Expired signed upload URLs cannot be reused after expiry.

### Publication and lifecycle
- Pending, failed, archived, and unpublished assets never appear on the public mini-site.
- Published assets require ready status, alt text, and an active property.
- Only one cover asset can be active per property.
- Archiving removes the asset from public resolution immediately.
- Signed read URLs expire and are not persisted.
- Property deactivation blocks publication and public media resolution without deleting historical metadata.

### Operational correctness
- Upload intent and audit event are atomic.
- Cover replacement is atomic.
- Failed finalization is retryable and idempotent.
- Cleanup uses Storage API operations and never direct SQL deletion from `storage.objects`.

4. Replay the full migration chain in an isolated Postgres/Supabase environment and run role, upload, publication, and cleanup tests.
5. Add backend upload-intent/finalization/public-resolution operations.
6. Add the Owner Desk media library UI and public mini-site gallery integration.
7. Run frontend build, backend tests, Storage policy tests, and Supabase advisors before merge/release.

## 11. Supabase platform notes

Supabase Storage object access is governed by RLS on `storage.objects`, independently from application-table policies. A private bucket is the correct default for unpublished business media. Signed URL delivery allows the backend to expose only published assets without making the whole bucket public.

Use non-upsert uploads. Supabase's current guidance notes that upsert requires additional SELECT/UPDATE policy checks and can produce confusing 403 errors when those checks are absent. Storage object deletion must go through the Storage API, not direct SQL deletion from `storage.objects`.
